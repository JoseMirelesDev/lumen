## 20:40 — perf study: por qué la app consume 1-9% CPU (voice chat)

**Category:** perf (investigación, sin cambios de código)

**Método (retomando el análisis que se perdió):** build release con símbolos + feature `mcp`
(`CARGO_PROFILE_RELEASE_DEBUG` NO — llenó el disco; release normal ya trae tabla de símbolos
y frame pointers). App real con MCP (`SLINT_EMIT_DEBUG_INFO=1 SLINT_MCP_PORT=43210`),
backend real (`lumen-backend.renymirelesd.workers.dev`, ya enlazado en settings.json).
`perf record -F99 -g --call-graph fp -T` + `/proc/<pid>/stat` para validar cruce.
Números en **% de 1 núcleo** (GNOME System Monitor muestra % del total de 4 núcleos → ÷4).

**Resultados (i5-4590, release, Skia/GL):**

| fase | % 1 núcleo | % del total (÷4) |
|---|---|---|
| idle chat (#general) | 1.2% | 0.3% |
| voice FOGATA + FastEnhancer-M | 45% | 11% |
| voice FOGATA sin denoiser (ns-only) | 32% | 8% |
| voice LISTA estático, sin denoiser | 25% | 6% |
| voice FOGATA sin denoiser, mic muteado | 16% | 4% |

**Causas atribuidas:**
1. **Denoiser neural (FastEnhancer-M) = ~13 pts (806/1350 samples = 60% de la fase)** —
   corre SIEMPRE en voice en el hilo tokio (`FastEnhancerDenoiser::process` → `fe_process_frame`,
   `fe_mhsa`, `fe_gru_step`, qgemm AVX2 fp16). Este es el grueso del rango 1-9% que veías.
2. **Render del campfire = ~16% aun con mic muteado** — el hilo main re-renderiza la escena
   continuamente: `render_to_canvas` + `visit_item` + `item_geometry` + `GrGLGpu::bindTexture`/
   `GrGLOpsRenderPass` + `dri3_swap_buffers`/`dri_flush` + mucha `malloc`/`_int_malloc`/`realloc`.
3. **Mic/captura casi no pesa** (18% activo vs 16% muteado ≈ +2%) — no es el pipeline de niveles.

**Hallazgo clave (por qué partial rendering no salva):** `SLINT_SKIA_PARTIAL_RENDERING=log`
muestra que SÍ está activo y repinta ~16% de la escena casi cada frame (picos a 100% periódicos),
pero la región del campfire se re-renderiza **a cada tick de animación** y cada re-render de Skia
(layout + upload GL + compose + allocs) cuesta ~16% de un núcleo en este CPU. No es full-scene
repaint; es redraw continuo de la escena animada con allocs GL por frame.

**Discrepancia con la medición del usuario (GNOME System Monitor, % del total):** idle 0.3% vs
su 1% (probablemente incluye el stream de audio out abierto + PipeWire, ~1% de un núcleo);
voice sin denoiser 4-8% vs su ~3% (mismo orden, factor ~2 — la diferencia es que él mide el
árbol completo del proceso en el System Monitor).

**Corrección al diary anterior:** la entrada 17:50 decía renderer femtovg — el código actual usa
`renderer-winit-skia` (Cargo.toml) y el diary estaba desactualizado. El denoiser real es
FastEnhancer-M/DeepFilterNet (tract), no GTCRN/sherpa-onnx como decía docs/performance.md.

**Recomendaciones (sin implementar):**
- Aislar/reducir el coste de render del campfire: el redraw continuo + allocs GL por frame es la
  vía de mejora principal (objetivo: amortiguar timers o subir el interval de animación).
- El denoiser neural es caro pero es la feature; verificar si el modelo M es el correcto vs un
  modelo menor si el presupuesto de CPU importa más que la calidad.
- Script harness: `scripts/perf-capture.sh` (perf record con timestamps + log de fases).

**Linked context:** retomado tras chat borrado; estudio de rendimiento pedido por el usuario.

## 21:45 — spike: render GL propio vía set_rendering_notifier (validación de la vía "hardware real")

**Category:** perf/experiment (spike de validación, no es la solución final)

**Contexto:** el estudio de perf mostró que el render del campfire por scene graph
cuesta ~16-32% de un núcleo (el hilo main paga traversal + propiedades + allocs por
tick de animación). La otra IA confirmó (verificado en source 1.17) que
`set_rendering_notifier` + `GraphicsAPI::NativeOpenGL` permite dibujar GL en el mismo
contexto de Slint (BeforeRendering = bajo, AfterRendering = sobre), y que
`BorrowedOpenGLTextureBuilder` + `cache-rendering-hint` son las piezas complementarias.

**Spike implementado** (`apps/lumen-slint/src/spike.rs`, gated por `LUMEN_SPIKE_GL=1`,
glow 0.17, shaders GLSL ES 300 — el contexto de Slint aquí es OpenGL ES 3.0, no desktop GL):
- 20 quads animados cuyo movimiento se calcula en el VERTEX SHADER (GPU), CPU solo
  setea uniforms por frame
- `slint::Timer` + `request_redraw()` a ~30 fps
- Guarda/restaura estado GL (blend, VAO, program)
- Se dibuja en `AfterRendering` (encima de la escena, antes del swap)

**Resultados (chat idle, % de 1 núcleo):**

| estado | % 1 núcleo |
|---|---|
| sin spike (base) | 1.2% |
| spike (20 quads GPU + request_redraw 30fps) | 13.6-14.4% |
| spike + cache-rendering-hint en el shell | 5.4% (parpadea la UI) |

**Validado:**
1. ✅ El notifier se dispara por frame con request_redraw; el contexto GL está activo
   y es seguro dibujar (quads visibles confirmados por el usuario)
2. ✅ La animación corre en GPU — el CPU no paga por partícula
3. ⚠️ **`request_redraw()` continuo fuerza re-render completo de la escena de Slint
   cada frame** (confirmado: +12-13% de un núcleo solo por eso, en `render_to_canvas` +
   ioctl + memmove). Es el límite conocido del mantenedor (sin buffer-age/swap-con-damage
   en Slint aún)
4. ⚠️ `cache-rendering-hint: true` en el shell reduce el costo (14.4→5.4%) PERO causa
   parpadeo visual (el layer cacheado se invalida/re-blitea en conflicto con el
   request_redraw + overlays) → revertido

**Aprendizajes:**
- El contexto GL de Slint aquí es **OpenGL ES 3.0** (GLSL `#version 300 es`; `330 core`
  no compila). El driver ES no expone `get_parameter_indexed_i32` → segfault si se usa
  (usar `window.size()` en vez de consultar el viewport).
- `Window` no es `Clone`; el timer usa `app.as_weak()` → `upgrade()` → `request_redraw`.
- El screenshot del MCP (`take_snapshot`) NO muestra el overlay GL — solo el framebuffer
  real (scrot) o el ojo humano lo ven.

**Conclusión de la vía:** el mecanismo "render propio conectado a Slint" funciona, pero
el `request_redraw` continuo tiene un coste fijo alto (~13% de un núcleo a 30 fps = re-render
completo de Slint). El layer-cache lo mitiga pero introduce parpadeo. La arquitectura final
debe decidir: (a) fogata en FBO/textura + BorrowedOpenGLTextureBuilder con redraw controlado,
(b) reducir la frecuencia de request_redraw al mínimo perceptible (p.ej. 15fps para brasas),
(c) aceptar el coste fijo del redraw en pantallas chicas, o (d) cache-rendering-hint selectivo
solo en el subárbol realmente estático (no en el shell con overlays).

**Linked context:** spike pedido por el usuario tras validar la vía con la otra IA
(set_rendering_notifier + BorrowedOpenGLTextureBuilder + cache-rendering-hint).

## 22:10 — experimento: cache-rendering-hint + overlay GL (resultado: incompatible)

**Category:** perf/experiment (negativo — descarta la vía del layer cache)

**Hipótesis (de la otra IA):** el parpadeo visto con cache + overlay GL se debe a que el
partial rendering de Slint trackea regiones sucias por buffer age para SU contenido, y el
dibujo GL externo es invisible para ese tracking → desincronización entre back buffers del
swap chain. La predicción: con `SLINT_SKIA_PARTIAL_RENDERING=0` (redraw completo, sin
buffer-age tracking) el parpadeo debería desaparecer.

**Experimento:** `cache-rendering-hint: true` en el shell + `SLINT_SKIA_PARTIAL_RENDERING=0`
+ spike GL (20 quads, 30 fps).

**Resultado (chat idle, % de 1 núcleo):**

| config | % 1 núcleo | UI visible | parpadeo |
|---|---|---|---|
| spike, sin cache, partial ON | 14.4% | sí | no |
| spike + cache, partial ON | 5.4% | sí | **sí** (hover) |
| spike + cache, partial OFF | 4.0% | **NO (solo quads)** | **sí** (hover) |

**Conclusión: `cache-rendering-hint` es incompatible con el overlay GL externo** en ambas
configuraciones. Con partial OFF además la escena de Slint deja de verse (solo los quads del
overlay) — el cache + redraw completo + AfterRendering rompen la composición. La hipótesis de
buffer-age NO se confirma como vía de arreglo: el conflicto es más profundo (el layer cacheado
de Skia y el dibujo GL directo compiten por el mismo framebuffer en cada frame).

**Estado final:** cache revertido del .slint; app corriendo estable con el spike
(LUMEN_SPIKE_GL=1, partial ON, sin cache) — UI normal + 20 quads GPU a 30 fps, ~14% de 1 núcleo
en chat idle (el coste es el redraw completo que Slint fuerza por request_redraw, no los quads).

**Vías restantes (documentadas, no decididas):**
1. Fogata en FBO/textura + `BorrowedOpenGLTextureBuilder`, redraw a la mínima frecuencia
   perceptible (15 fps) — VALIDAR a ojo lado a lado antes de aceptar (stutter en puntos de luz)
2. Aceptar el coste fijo del redraw completo (~14% de 1 núcleo a 30 fps) como precio del
   efecto en GPU, con la fogata fuera del scene graph (el árbol restante es más chico)
3. Sin cache-rendering-hint — descartado por parpadeo en ambas configs de partial rendering

**Linked context:** experimento pedido por el usuario para resolver el parpadeo que introdujo
el cache-rendering-hint del spike anterior; feedback de la otra IA sobre buffer-age/swap-damage.

## 23:40 — hallazgo decisivo: rotar el source de 1 Image mantiene partial rendering y cuesta ~0.2%

**Category:** perf/experiment (RESUELVE el objetivo de UI: 1% del total)

**Hipótesis corregida:** las 4 IAs convergieron en "FBO off-screen + BorrowedOpenGLTextureBuilder +
request_redraw". Pero medí que el request_redraw continuo + notifier (que desactiva partial
rendering) cuesta ~14% SIN importar el tamaño del árbol — esa vía era un callejón sin salida.

**Experimento decisivo:** 1 sola Image cuyo `source` rota cada 80ms (timer de .slint, SIN
notifier, partial rendering ON).

**Resultado (FOGATA conectado, % de 1 núcleo):**

| config | total proceso | main thread |
|---|---|---|
| 34 partículas (original) | 12.25% | ~6.5% |
| 1 Image estático | 0.80% | ~0.2% |
| **1 Image rotando 80ms (partial ON)** | **0.86%** | **~0.2%** |
| 1 Image + notifier/request_redraw | 14.26% | ~14% |

Perf confirma: con la Image rotando, main = 4/32 samples (0.2%); el resto es cpal_alsa_out +
pw-data-loop (audio out, fuera de alcance por instrucción del usuario).

**Conclusiones:**
1. El costo NO es "renderizar por cada cambio" — es (a) el nº de items del árbol (34→1 =
   12.25%→0.8%) y (b) el notifier que desactiva partial rendering (1 Image + notifier = 14%).
2. **Animar 1 Image rotando su source con partial rendering ON cuesta ~0.86%** — cumple el
   objetivo de 1% del total para la UI.
3. La vía correcta NO es FBO + request_redraw + notifier (callejón). Es **generar los frames
   de partículas en Rust (matemática del .slint → Image::from_rgba8) y rotar el source** con
   partial rendering activo. La simulación sigue viva (se calcula cada frame), sin archivos.

**Estado:** .slint con el experimento (1 Image `fire-frame` rotando entre 2 sprites); el
ParticleLayer real queda comentado temporalmente. Falta: reemplazar el placeholder de 2
sprites por los N frames reales de partículas generados en Rust.

(que estimaron "2-4%" para el FBO sin medir el request_redraw+notifier).
