# 2026-08-13 — Backend V2: implementación completa (Fases 1-6)

Implementado el plan `plans/backend-v2` fase por fase con verificación tras
cada una. Backend (apps/backend), protocolo (packages/protocol), crates
(lumen-core, lumen-voice) y UI Slint (lumen-desktop).

## Fase 1 — Seguridad
- `src/rate-limit.ts` (Cache API sliding window, per-route + wildcard 100/min),
  CORS restringido (ALLOWED_ORIGINS), body limit 1 MB (con exención para
  uploads de assets en Fase 4), `GET /api/health`, refresh tokens rotativos
  (ADR-0007) con `POST /api/auth/refresh|logout` y `DELETE /api/auth/sessions`,
  access token TTL 1h. Cliente: refresh hook en ApiClient (401 → refresh →
  retry una vez), persistencia del refresh token en settings.json, logout
  revoca en el servidor.
- Desviación documentada: escape hatch dev `LUMEN_RATE_LIMIT_DISABLED`
  (solo local, .dev.vars) porque el smoke suite registra ~10 usuarios y el
  límite de register es 3/h. El limiter se verifica en unit tests (fake

  (ADR-004): flush a message_blocks a 50 mensajes o alarm 5 min; ACK +

- **Dev server inestable**: wrangler 4.118 arrastraba `miniflare 5.20260730.0-

  ALL PASS y server estable.

- Cliente: presence.rs (WS + reconnect con backoff), CoreEvents de presencia,

## Fix posterior — subscribe-ack (race en broadcast de chat)

Hallazgo durante re-verificación: `pnpm smoke` era **flaky** (fallo
intermitente en `chat RT: sender gets chat-ack`). Causa raíz: el test
enviaba `subscribe(wsP)`, `subscribe(wsQ)` y `chat(wsP)` sin esperar que
los subscribes se procesaran. El DO procesa en orden de llegada, pero el
orden de entrega entre sockets no está garantizado: `chat` podía llegar al
DO antes que `subscribe` de wsQ → el filtro de broadcast (suscripciones en
attachment, workerd#958) descartaba el mensaje para wsQ → timeout.

Fix: el DO responde `subscribe-ack { channelId }` al procesar cada
subscribe; el smoke (y el cliente) esperan el ack antes de enviar/esperar
chat del canal. Determinista, sin delays frágiles.

Archivos: `PresenceHubDO.ts` (caso subscribe), `packages/protocol`
(`subscribe-ack`), `protocol.rs` + `presence.rs` + `event.rs`
(`SubscribeAck` variant + CoreEvent), `smoke-ws.mjs` (espera ambos acks),
`controller.rs` (arm del ack, no-op documentado), `presence-v2.md`.

Verificación: 6/6 corridas consecutivas de `pnpm smoke` ALL STEPS PASSED
(antes: ~2/3 fallaban). Unit tests 35/35, typecheck y cargo check limpios.

## Deploy a producción + bug de rate limit (1101)

**Desplegado:** `https://lumen-backend.renymirelesd.workers.dev` (version
e8b40121, 2026-08-14). Recursos: R2 bucket `lumen-assets` creado,
migraciones 0003-0007 aplicadas al D1 remoto (datos 0001-0002 intactos),
secrets OAuth Google subidos (client_id real, OAUTH_CALLBACK_URL,
WEB_CLIENT_URL).

**Bug crítico encontrado en producción (no reproducía local):** el rate
limiter (Cache API) usaba `caches.default.match(key)` con key
`rl:<ip>:GET:<path>` — el Cache API exige URL completa o Request; un string
no-URL lanza TypeError → excepción no capturada (corre fuera del try/catch
del fetch handler) → **error 1101 en TODA la API**. En local no apareció
porque `LUMEN_RATE_LIMIT_DISABLED=true` salta el path; los unit tests
stubban `caches` con un mock permisivo. Fix: key como URL sintética
`https://rate-limit/<encoded>`.

Verificado localmente con el limiter ACTIVADO (404s normales, 302 OAuth,
429 en el 4º register) y en producción tras redeploy (el 500 residual era
el edge cache de workers.dev sirviendo la versión vieja — gotcha conocido,
esperar ~60s).

**Verificación de producción** (el smoke completo no aplica: triparía el
rate limit de register 3/h/IP, comportamiento correcto): health ok, register
201, login 200, /api/me, create server 201, realtime config con TURN real
(Cloudflare Realtime), presence WS upgrade 101 + ready snapshot.

**Nota:** el smoke E2E completo queda como verificación local
(`wrangler dev` + `pnpm smoke`, con `LUMEN_RATE_LIMIT_DISABLED=true` en
.dev.vars). Contra producción, usar la suite mínima de smoke-ws.mjs
(health/auth/presence) o un token de test con límites elevados.
